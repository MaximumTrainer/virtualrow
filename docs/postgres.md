# Postgres on Neon — setup, secrets, TLS posture, rotation (issue #441)

VirtualRow's server-side persistence lives on Neon's free tier. Today it holds
nothing — the app is still fully browser-side — but this issue provisions the
hosting, the credentials, and the CI healthcheck so #37 (schema + migrations
+ `PersistencePort`) can land against a known-good database without doing any
of the ops work at merge time.

This document is the FR6 doc named in #441: it explains where the database
lives, the branch / role / TLS posture, how to rotate any secret without a
code change, and how to respond to a suspected credential exposure.

## Where the database lives

- **Provider**: [Neon](https://neon.tech), free tier.
- **Project name**: `virtualrow`.
- **Region**: `aws-us-east-2` (Ohio) — the default recommended by #441 FR1.
  If a later measurement shows most rowers are east of the Atlantic, a follow-up
  can migrate; the project id survives a region change (Neon issues a new
  endpoint but the project stays).
- **Branches** (D2): two live branches per FR1 — `main` (production) and
  `dev`. Neon's copy-on-write branch model means the `dev` branch shares
  storage with `main` at zero cost until it diverges; PR CI branches (a
  follow-up) will be short-lived children of `dev`.
- **Compute auto-suspend**: on (Neon's default). A weekly healthcheck
  (`neon-healthcheck.yml`) wakes the compute long enough to run `SELECT 1`.

The Neon project id and console URL are NOT in this repo — they live in Dan's
1Password. If you need them, ask him; a maintainer with the secrets can
recover the id from any `NEON_*_URL_*` secret's host (`ep-<id>.aws-us-east-2.neon.tech`).

## Branch and role model

Every branch of the Neon project carries the three roles below (D3). Each role
has the narrowest grant that makes it work, so a single-secret compromise
never gives more than that role's blast radius.

| Role | Grants on this branch | Used by |
|---|---|---|
| `virtualrow_owner` | Owner of every schema; DDL / migrations | The future `db-migrate.yml` workflow (#37), opening a short-lived connection per run |
| `virtualrow_app` | DML on application schemas; no DDL | The future browser-facing proxy (#441 D4 follow-up) at runtime |
| `virtualrow_ci_readonly` | `CONNECT` on `neondb` + `USAGE` on `public`; no table grants | The healthcheck workflow (`neon-healthcheck.yml`) — reads nothing, runs `SELECT 1` |

Passwords are generated by Neon (≥ 32 chars, unique per role per branch) and
authenticate with **SCRAM-SHA-256**. No role is ever configured to accept
`password` or `md5` — Neon's default rejects those.

## Connection security posture (NFR-S1–S9)

Every URL that reaches Neon MUST carry both of these query parameters:

```
sslmode=verify-full&channel_binding=require
```

- **`sslmode=verify-full`** (NFR-S1) verifies the certificate chain against
  the system trust store **and** verifies the server hostname matches the
  certificate SAN. `require` alone accepts any cert; `verify-ca` skips the
  hostname check. Neon's endpoint certs are issued by a public CA present in
  the standard `ca-certificates` bundle used by GitHub-hosted runners and
  Cloudflare Workers, so **no custom CA bundle is committed** to this repo.
- **`channel_binding=require`** (NFR-S2) forces the SCRAM exchange to bind to
  the TLS channel (SCRAM-SHA-256-PLUS), which defends the login against MITM
  even if a rogue CA is somehow trusted. Neon supports this on every tier.

The healthcheck asserts both at connection time and against `pg_stat_ssl` on
the live connection — see AC11 and AC12 in #441. A downgrade to `require` or a
URL missing `channel_binding=require` MUST fail red; if it doesn't, the
healthcheck is lying.

**Neon's free tier does not offer IP allowlisting.** Access control is
credential + TLS only. If the project is ever upgraded to a tier that supports
allowlisting, a follow-up can narrow the surface further.

## GitHub secrets (FR3)

Only these seven secret **names** live in this repo (in this doc, in
`neon-healthcheck.yml`, and in any future workflow that touches Neon). The
**values** live only in GitHub Actions' encrypted store.

| Secret name | Role / branch | Contains |
|---|---|---|
| `NEON_DATABASE_URL_MAIN` | `virtualrow_app` on `main` | `postgres://virtualrow_app:…@ep-…-pooler.aws-us-east-2.neon.tech/neondb?sslmode=verify-full&channel_binding=require` |
| `NEON_DATABASE_URL_DEV` | `virtualrow_app` on `dev` | Same shape, dev endpoint |
| `NEON_MIGRATION_URL_MAIN` | `virtualrow_owner` on `main` | Same shape, owner role |
| `NEON_MIGRATION_URL_DEV` | `virtualrow_owner` on `dev` | Same shape, owner role, dev endpoint |
| `NEON_CI_READONLY_URL` | `virtualrow_ci_readonly` on `main` | Same shape, read-only role |
| `NEON_API_KEY` | Neon personal API key (D1) | Used by any workflow that creates per-PR branches later |
| `NEON_PROJECT_ID` | Plain project identifier | Not sensitive; stored beside the rest so it rotates together |

Each `*_URL_*` secret **must** include both `sslmode=verify-full` **and**
`channel_binding=require`. The healthcheck refuses a URL missing either
(AC11 / AC12).

## Workflow → secret mapping (auditable from the repo)

| Workflow | Reads | Purpose |
|---|---|---|
| `.github/workflows/neon-healthcheck.yml` | `NEON_CI_READONLY_URL` | Weekly `SELECT 1`; refuses to run if the secret is missing or lacks the TLS parameters |
| (future) `db-migrate.yml` (#37) | `NEON_MIGRATION_URL_MAIN` OR `NEON_MIGRATION_URL_DEV` | Applies pending migrations against the target branch |
| (future) proxy build (#441 D4 follow-up) | `NEON_DATABASE_URL_MAIN` | Server-side only — never reaches the browser |

The Pages deploy (`.github/workflows/deploy-pages.yml`) does not read any
`NEON_*` secret — its only secret is `INTERVALS_OAUTH_CLIENT_ID` and that's
unchanged.

**None of the `NEON_*` secrets are ever exposed as a `VITE_` variable, ever
read by `npx vite build`, and ever written into `dist/`** (NFR-S5, AC10). A
grep over the built bundle for `neon.tech`, `postgres://`, or any of the role
names returns nothing — the healthcheck extends to this by making the grep
part of the CI (see the workflow).

## Setting up Neon (Dan's Phase 1 walkthrough)

If you're not Dan, stop reading here — this is the "how the DB was created"
runbook, not something a contributor re-runs.

### 1. Create the project

1. Sign in to [console.neon.tech](https://console.neon.tech) as the account
   named in D1 (Dan's personal account for now).
2. **Create Project**:
   - Name: `virtualrow`.
   - Postgres version: latest LTS Neon offers (currently 17).
   - Region: `AWS US East 2 (Ohio)`.
   - Compute: free tier defaults.
3. Neon auto-creates a `main` branch and a default `neondb` database. Confirm
   both exist under **Branches** and **Databases**.

### 2. Create the `dev` branch

1. Under **Branches**, click **Create branch**.
2. Source: `main`, most recent LSN.
3. Name: `dev`.
4. Leave compute settings at their defaults.

### 3. Create the three roles on each branch

For each of `main` and `dev`, in **Roles**:

1. Create `virtualrow_owner` — Neon generates the password. Copy it to
   1Password immediately; you cannot retrieve it later.
2. Create `virtualrow_app` — same.
3. Create `virtualrow_ci_readonly` — same.

Then in the Neon SQL Editor, connect as the `virtualrow_owner` you just
created (Neon's console injects the correct connection string; no local
`psql` needed) and run:

```sql
-- On both branches. Neon's default database is `neondb`.
GRANT CONNECT ON DATABASE neondb TO virtualrow_app, virtualrow_ci_readonly;
GRANT USAGE ON SCHEMA public TO virtualrow_app, virtualrow_ci_readonly;
GRANT CREATE, USAGE ON SCHEMA public TO virtualrow_owner;

-- No table grants for the readonly role until it needs one. The healthcheck
-- runs `SELECT 1` which does not need any table access.
```

Verify (also in the SQL Editor, connecting as `virtualrow_ci_readonly`):

```sql
SELECT 1;                                    -- must succeed
CREATE TABLE probe_should_fail (id int);     -- must fail: permission denied
SELECT * FROM pg_class LIMIT 1;              -- read of a system view is fine
```

The `CREATE TABLE` failing is AC9 in #441 — leave a note in your Neon activity
log so a future audit can find it.

### 4. Build the seven URL secrets

For each `*_URL_*` secret, take Neon's own connection string for the target
role/branch, then **append `?sslmode=verify-full&channel_binding=require`**
(or if Neon's string already carries a query string, add `&sslmode=verify-full&channel_binding=require`).

Example shape (real values redacted):

```
postgres://virtualrow_app:REDACTED@ep-cool-fire-12345.us-east-2.aws.neon.tech/neondb?sslmode=verify-full&channel_binding=require
```

Use the **pooled endpoint** (`-pooler` suffix) for `NEON_DATABASE_URL_*`
(the app roles will be pool-friendly at runtime). Use the **direct endpoint**
(no suffix) for `NEON_MIGRATION_URL_*` and `NEON_CI_READONLY_URL` — migrations
and the healthcheck each open exactly one short-lived connection and close it,
so pooling adds overhead without help.

Test each URL from your terminal:

```bash
# Requires psql 15+ on your machine.
psql "postgres://…?sslmode=verify-full&channel_binding=require" -c "SHOW ssl"
```

You should see `on` for `ssl` and no TLS warnings from psql. If verify-full
fails, the URL is misspelled — do not fall back to `require` to make it work.

### 5. Populate the GitHub secrets

For each name in the FR3 table above:

1. In this repo, go to **Settings → Secrets and variables → Actions → New
   repository secret**.
2. Paste the value verbatim. Do not add trailing whitespace; GitHub trims but
   `psql` does not.
3. Save.

Two extras beyond the seven URLs:

- `NEON_API_KEY` — from Neon **Account settings → API keys → Create**.
  Scoped to the `virtualrow` project if Neon offers it on your tier; otherwise
  a personal-scope key is acceptable (NFR-S8 flags this). Copy immediately.
- `NEON_PROJECT_ID` — from the Neon console URL (the segment after
  `console.neon.tech/app/projects/`).

### 6. Manually verify the healthcheck

After all secrets are set, from the GitHub Actions tab manually dispatch the
`Neon healthcheck` workflow. It should:

- Pass green: `ssl=on`, TLS version ≥ 1.2, `channel_binding=SCRAM-SHA-256-PLUS`,
  `SELECT 1` returns 1.
- Fail loudly if you unset `NEON_CI_READONLY_URL` (AC4).
- Fail loudly if you swap in a URL with `sslmode=require` or without
  `channel_binding=require` (AC11 / AC12).

### 7. Turn on secret scanning + push protection (NFR-S6 / AC14)

In **Settings → Code security and analysis**, enable:

- **Secret scanning**
- **Push protection** (rejects a push that includes a detected secret)

Both are free for public repos. Confirm both are on before closing #441.

## Rotating a single secret (NFR-S7)

Any `NEON_*_URL_*` secret can be rotated end-to-end in five minutes with
zero code changes. Do this on any suspected exposure, on any change to who
has access to the repo secrets, and on the schedule your compliance calendar
tells you.

1. **Neon console → Roles →** the affected role.
2. Click **Reset password**. Neon generates a new one; copy it.
3. Assemble the new URL by pasting the new password into the same shape used
   in step 4 above. Keep the `?sslmode=verify-full&channel_binding=require`
   query string.
4. **GitHub → Settings → Secrets and variables → Actions →** the affected
   secret **→ Update**. Paste the new URL.
5. Manually dispatch `neon-healthcheck.yml`; it must go green.

Rotating a single secret MUST NOT require rotating another (NFR2). If any
workflow refuses to run after a rotation, something has cross-wired the
credentials — fix that before continuing.

To rotate the `NEON_API_KEY`:

1. In Neon **Account settings → API keys**, revoke the current key.
2. Create a new one, scoped as before.
3. Update `NEON_API_KEY` in the repo secrets.

To rotate `NEON_PROJECT_ID`: you cannot — a project id is stable for the
project's lifetime. If a project needs to move, it becomes an "add a new
project + carve over storage" operation which is out of the scope of a
rotation runbook.

## Incident runbook (NFR-S7 / AC15)

Follow this if a `NEON_*_URL_*` value is exposed (pasted into a public
comment, checked into a fork, screenshotted into a bug report). Total time:
under 10 minutes on a normal connection.

1. **Revoke immediately**. Neon **Roles → the affected role → Reset password**.
   This invalidates the exposed URL the moment it commits, before you've
   updated anything else — every process still using the old URL will fail on
   its next connection.
2. **Rotate GitHub secret** per the runbook above (steps 3–4).
3. **Re-run healthcheck** manually.
4. **Audit access**: Neon **Monitoring → Activity log** — look for connections
   from IPs you don't recognise between when the URL was exposed and when
   it was revoked.
5. **Report** in the incident channel with:
   - The role whose password was rotated.
   - The window during which the exposed URL was valid.
   - Any suspicious activity found in the audit.
6. **If the exposed value was `NEON_API_KEY`**: rotate it too (any workflow
   using the API to spin up per-PR branches could otherwise be replayed with
   an attacker's own script).

Never delete the exposed value from its original location alone — a revocation
in the audit trail is what makes it safe; a delete makes it invisible but
still functional if it was already scraped.

## Contributor local development (FR8)

You never receive a shared `NEON_*` value. To work on a feature that touches
Postgres:

1. In your own Neon account, create a **fork** of the shared `dev` branch,
   or create a throwaway project pointed at whatever schema you need.
2. In your working copy, put the connection string in `.env.local` (already
   gitignored, per AC8):

   ```
   VIRTUALROW_DEV_DB=postgres://…?sslmode=verify-full&channel_binding=require
   ```
   
   Use a repo-local variable name (`VIRTUALROW_DEV_DB`, not `NEON_DATABASE_URL_*`)
   so it can never be confused with a shared secret name.
3. Verify your own connection uses verify-full:

   ```bash
   psql "$VIRTUALROW_DEV_DB" -c "SHOW ssl"
   ```

4. Do not paste `VIRTUALROW_DEV_DB`'s value into a PR body, an issue, a
   commit message, a code comment, or a Slack thread. Only the secret name
   goes into any of those places.
